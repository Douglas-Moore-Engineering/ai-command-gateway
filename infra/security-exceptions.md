# Scoped static-check dispositions

These four Checkov dispositions apply to this nonproduction implementation. They are engineering decisions, not customer security acceptance or proof of production readiness. No severity-based assurance is claimed from an offline scanner run. Each suppression sits beside the affected resource; other checks remain enabled.

| Check | Resource | Disposition and evidence | Remaining work |
|---|---|---|---|
| CKV_AZURE_36: trusted Microsoft services bypass | Blob account | Deliberately keep `networkAcls.bypass: None`, `defaultAction: Deny`, and public access disabled. The job uses its private endpoint and managed identity; no service requires a firewall bypass. Enabling a broader bypass solely to satisfy the rule would loosen this design. | Verify private DNS and Blob access from the deployed job. |
| CKV_AZURE_43: account naming | Blob account | Checkov scans the child module without resolving `storageName`. [main.bicep](main.bicep) supplies `staicg${uniqueString(resourceGroup().id, workloadName)}`. The literal prefix is six characters; `uniqueString` yields thirteen lowercase alphanumeric characters. The resulting nineteen characters satisfy the account's 3-24 lowercase-letter/digit rule. No raw workload-name characters enter the resource name. | Check global name availability for the actual target during deployment validation. |
| CKV_AZURE_166: registry quarantine | Private Premium registry | Automatic quarantine is a preview feature that requires a working scan-and-release workflow. Enabling its flag alone would leave pushed images unavailable to ordinary image pulls. That workflow is not implemented here. Registry admin/anonymous/public access is disabled; the job has only `AcrPull` and consumes a reviewed immutable digest. Digest pinning does not establish image safety or authenticity. | Before production use, implement and verify image vulnerability scanning, provenance/signature verification and release enforcement. For this nonproduction increment, an operator must review a scan for the exact digest before publishing/starting the job. No scan is claimed until its evidence is recorded. |
| CKV_AZURE_206: storage geo-replication | Blob account | The implemented `Standard_ZRS` copies data across availability zones in the selected region. Checkov 3.3.29 accepts only GRS/RAGRS/GZRS/RAGZRS for this rule. Cross-region residency, recovery objectives and the secondary region have not been defined for these reproducible nonproduction artifacts. | Establish data residency and recovery requirements before choosing geographic replication. Azure region support for ZRS remains a deployment precondition. |

The initial LRS choice was strengthened to `Standard_ZRS`; this does not satisfy a check that specifically requires geographic replication. There is no high-availability claim for the single-replica job.

References: [storage naming rules](https://learn.microsoft.com/azure/azure-resource-manager/management/resource-name-rules#microsoftstorage), [uniqueString](https://learn.microsoft.com/azure/azure-resource-manager/bicep/bicep-functions-string#uniquestring), [ACR quarantine FAQ](https://learn.microsoft.com/azure/container-registry/container-registry-faq#how-do-i-enable-automatic-image-quarantine-for-a-registry), [private registry access](https://learn.microsoft.com/azure/container-registry/container-registry-private-endpoints).
